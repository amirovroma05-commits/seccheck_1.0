# SecCheck — техническое задание

## 0. Контекст

Курсовая работа «Методы и средства защиты информации в компьютерных сетях», МТУСИ.
По методичке программа должна содержать пять модулей:

1. проверка наличия подключения к интернету;
2. проверка наличия установленных межсетевого экрана (МЭ) и антивируса (АВ);
3. проверка работоспособности МЭ;
4. проверка работоспособности АВ (тестовый файл EICAR);
5. вывод результатов.

Методичка разрешает консольный интерфейс. Примеры в ней на C# под Windows: мы их не копируем,
но покрываем те же функции. Кроме кода нужны блок-схемы всех алгоритмов (ГОСТ 19.701-90).
Поэтому алгоритмы ниже записаны пошагово, и код обязан им соответствовать.

## 1. Область работ

- Linux с systemd (Debian, Ubuntu, Astra Linux и подобные). Логики под конкретный
  дистрибутив нет.
- Только консольный интерфейс: интерактивное меню. Флаги командной строки: `--help`,
  `--version`, `--config PATH`, `--products PATH`, `-v`/`--verbose`.
- Python 3.5+ (на стенде 3.5; чтобы работало и на старых дистрибутивах), только стандартная
  библиотека. Совместимость проверяется инструментом vermin (раздел 10).
- Кодировка везде UTF-8 явно: в 3.5 при локали C/POSIX (sudo, cron, ssh с `LANG=C`)
  кодировка по умолчанию — ASCII. Текстовые файлы открываются с `encoding="utf-8"`,
  вывод команд декодируется `run_cmd`, а `main.py` при старте переоткрывает `sys.stdout`
  и `sys.stderr` в UTF-8, если их кодировка другая (раздел 7, M5, шаг 1).

## 2. Стенд

- Виртуальная машина с Linux на systemd.
- Запуск программы от root (`sudo`). Без root проверка M3 не может прочитать правила МЭ.
- Средства защиты на стенде: ClamAV с `clamonacc` (проверка при доступе) и `ufw`.
  Опционально Dr.Web для Linux или Kaspersky Endpoint Security для Linux (KESL).
- Тестовое правило МЭ автор создаёт вручную по командам из README.md.

## 3. Структура проекта

```
seccheck/

├── common.py           # run_cmd(), is_root(), os_info(), load_config(), статусы

├── products.json       # список продуктов для M2
```

Каждый модуль проверки содержит функцию `run(cfg)`, где `cfg` — его секция файла настроек
(раздел 6). Значений настроек по умолчанию в коде нет. Модули могут сами печатать
(прогресс ожидания в M4). M2 дополнительно получает список продуктов:
`run(cfg, products)`.

## 4. Статусы и формат результата

Статусы — строковые константы в `common.py`:

| Константа | Смысл |
|---|---|
| `OK` | проверка пройдена |
| `WARNING` | работает частично / есть замечания |
| `FAIL` | средство защиты не сработало / отсутствует |
| `INCONCLUSIVE` | вывод сделать нельзя (нет сети, недоступна цель) |
| `NOT_RUN` | проверку не запускали |
| `ERROR` | сбой программы или нехватка прав |

Каждая проверка отвечает только на свой вопрос: M1 — есть ли интернет, M2 — есть ли АВ
и МЭ, M3 — блокирует ли МЭ запрещённое соединение, M4 — реагирует ли АВ на тестовый файл.
В вывод проверки попадает только то, что отвечает на её вопрос.

`run()` возвращает кортеж `(статус, краткие, подробности)`:
- `краткие[0]` — результат без названия проверки, например `"есть"`;
- `краткие[1:]` — строки, которые печатаются всегда: найденные продукты в M2, подсказки
  при не-OK («Проверьте…», «Создайте…»), предупреждение о неудалённом файле в M4;
- `подробности` — печатаются только с флагом `-v`.

`main.py` печатает итог в виде `<метка> <id>  <Название>: <результат>`, под ним краткие
строки, с `-v` — подробности (отступ 9 пробелов). Название берётся из списка `CHECKS`
в `main.py` и одинаково в меню, в строке результата и в отчёте: M1 «Подключение
к интернету», M2 «Наличие АВ и МЭ», M3 «Работоспособность МЭ», M4 «Работоспособность АВ».
Исключение в модуле → `ERROR` «<Название>: ошибка проверки (<тип>: <текст>)».

## 5. Общие функции (`common.py`)

| Функция | Как работает |
|---|---|
| `run_cmd(cmd, timeout)` | `subprocess.run(cmd, stdout=PIPE, stderr=PIPE, timeout=…, env=окружение + LC_ALL=C)`, без `shell=True`. Вывод получается байтами и декодируется `decode("utf-8", "replace")`: текстовый режим декодировал бы по локали, а при `LANG=C` в 3.5 это ASCII. Возвращает `(код, stdout, stderr)`. `FileNotFoundError` → код `CMD_NOT_FOUND` (−1), `TimeoutExpired` → `CMD_TIMEOUT` (−2) |
| `is_root()` | `os.geteuid() == 0` |
| `os_info()` | значение `PRETTY_NAME` из `/etc/os-release`; если его нет — «Linux». Только для заголовка отчёта |
| `load_config(path)` | загрузка и проверка файла настроек (раздел 6) |

`LC_ALL=C` нужен потому, что вывод `systemctl`, `iptables` и других утилит локализован,
а программа разбирает только английский.

## 6. Настройки (`config.json`)

Узлы, порты и таймауты проверок хранятся во внешнем JSON-файле. Файл обязателен:
значений по умолчанию в коде нет, без файла программа не запускается.

Где программа берёт файл:
1. `--config ПУТЬ`, если указан;
2. иначе `/etc/seccheck/config.json` (`common.DEFAULT_CONFIG_PATH`).

`config.json` в репозитории — полный набор ключей с рабочими значениями. `install.sh`
копирует его в `/etc/seccheck/config.json` только при первой установке (раздел 8).

| Секция | Ключ | Тип и ограничения | Значение в репозитории |
|---|---|---|---|
| `network` | `ru_hosts` | непустой список имён узлов | `["ya.ru", "vk.com"]` |
| | `foreign_hosts` | непустой список имён узлов | `["example.com", "github.com"]` |
| | `tcp_port` | порт | 443 |
| | `tcp_timeout_s` | таймаут | 3 |
| | `ping_timeout_s` | таймаут, только целое число (передаётся в `ping -W`, старые версии ping принимают только целое) | 2 |
| `presence` | `cmd_timeout_s` | таймаут одной команды `systemctl` | 5 |
| `firewall_test` | `host` | имя узла | `"ya.ru"` |
| | `control_port` | порт, ≠ `test_port` | 443 |
| | `test_port` | порт | 80 |
| | `timeout_s` | таймаут одного подключения и одной команды `nft`/`iptables` | 3 |
| `antivirus_test` | `eicar_dir` | `null` или абсолютный путь к существующему каталогу | `null` |
| | `eicar_timeout_s` | таймаут | 30 |
| | `poll_interval_s` | таймаут | 1 |

- **Порт** — целое число 1..65535.
- **Таймаут** (и интервал) — число (int или float, но не `true`/`false`), больше 0
  и не больше 300 секунд.
- **Имя узла** — полностью соответствует `^[A-Za-z0-9][A-Za-z0-9.-]*$`, не длиннее 253
  символов. Имена узлов передаются в `ping`, запущенный от root: имя не может начинаться
  с «-», поэтому `ping` не примет его за ключ (например, `-c100`).
- **`eicar_dir`**: M4 создаёт внутри него свой подкаталог (`tempfile.mkdtemp`) и удаляет
  только свой файл и свой подкаталог; сам `eicar_dir` и всё прочее в нём не трогает.

Каждый модуль получает свою секцию явно: `check_network.run(config["network"])`,
`check_presence.run(config["presence"], products)`,
`check_firewall.run(config["firewall_test"])`,
`check_antivirus.run(config["antivirus_test"])`.

Алгоритм загрузки (`common.load_config(path)`, выполняется один раз при старте `main.py`):
1. Файла нет → ошибка «Файл настроек не найден: <путь>. Установите программу
   (sudo ./install.sh) или укажите файл: --config ./config.json».
2. Прочитать файл как JSON (UTF-8). Ошибка чтения или синтаксиса → ошибка.
3. Корень — объект. Есть секция не из таблицы → ошибка «неизвестная секция».
4. Взять следующую секцию из таблицы. Её нет или она не объект → ошибка.
5. Есть ключ не из таблицы → ошибка «неизвестный ключ» (так ловятся опечатки).
6. Для каждого ключа таблицы: нет ключа → ошибка с его именем; значение не проходит
   проверку типа и ограничений → ошибка.
7. Секции закончились? Нет → шаг 4.
8. `control_port` равен `test_port` → ошибка.
9. Вернуть словарь настроек.

Любая ошибка — `ValueError` с текстом, где указаны путь к файлу, секция, ключ и что
не так, например `config.json: секция "network", ключ "tcp_port": ожидается целое число
от 1 до 65535, получено 70000`. `main.py` выводит сообщение в stderr и завершается
с кодом 2 без трассировки, до показа меню.

## 7. Модули проверок

### M1. Проверка подключения к интернету (`check_network.py`)

Узлы делятся на две группы, чтобы отличить полный доступ от ограниченного (белые списки
мобильных операторов, блокировки). ICMP часто режется, поэтому решение принимается по TCP.

Настройки: секция `network` — `ru_hosts`, `foreign_hosts`, `tcp_port`, `tcp_timeout_s`,
`ping_timeout_s`.

Алгоритм:
1. Составить список узлов из групп `ru_hosts` и `foreign_hosts`.
2. Для каждого узла: `ping -c 1 -W ping_timeout_s` через `run_cmd` (результат только
   для сведения).
3. Для того же узла: TCP-подключение к `tcp_port` с таймаутом `tcp_timeout_s`
   (`socket.create_connection`). Ошибку DNS (`socket.gaierror`) запомнить отдельно.
4. Группа доступна, если хотя бы один её узел ответил по TCP.
5. Ни одна группа не доступна → `FAIL` «нет». Если у всех узлов ошибка DNS, добавить
   в подробности «Не работает DNS: ни одно имя узла не разрешилось».
6. Доступна одна группа → `WARNING` «ограничено (доступны только российские узлы)» или
   «ограничено (доступны только зарубежные узлы)».
7. Доступны обе → `OK` «есть».
8. Подробности (только `-v`): по каждому узлу ICMP да/нет, TCP да/нет, время подключения
   в мс. Если TCP работает, а ICMP нет ни у одного узла, добавить «ICMP блокируется».

Кратких строк под итогом у M1 нет. Все итоги: `есть`, `ограничено (доступны только
российские узлы)`, `ограничено (доступны только зарубежные узлы)`, `нет`.

Подключения выполняются последовательно (так проще объяснить).

### M2. Наличие АВ и МЭ (`check_presence.py`)

Отвечает только на вопрос, есть ли в системе АВ и МЭ. Работают ли они, проверяют M3 и M4,
поэтому в выводе M2 нет слов про защиту, фильтрацию и работу.

В Linux нет единого реестра средств защиты (как Центр безопасности Windows), поэтому
известные продукты ищутся по файлам и службам systemd из списка `products.json`.
Продукт найден, если есть хотя бы один его файл или установлена хотя бы одна его служба.

#### Файл продуктов `products.json`

Список продуктов хранится во внешнем файле. По умолчанию это `products.json` в каталоге,
где лежит `main.py` (`os.path.dirname(os.path.realpath(__file__))`); флаг
`--products PATH` задаёт другой файл. Формат: `{"products": [ {...}, ... ]}`.

| Поле | Обяз. | Тип | Смысл |
|---|---|---|---|
| `id` | да | непустая строка, уникальна | идентификатор |
| `name` | да | непустая строка | название для отчёта |
| `kinds` | да | непустой список из `"antivirus"`, `"firewall"` | вид продукта |
| `services` | да | список имён служб (может быть пустым) | любая установлена → продукт найден |
| `files` | да | список абсолютных путей (может быть пустым) | любой существует → продукт найден |
| `verified` | нет | bool, по умолчанию `false` | имена служб и пути проверены на реальной системе |
| `notes` | нет | строка | примечание, в отчёт не выводится |

Продукты в поставке: ClamAV (`clamav-daemon`, `/usr/sbin/clamd`, `verified: false`),
ufw (`ufw`, `/usr/sbin/ufw`, `verified: true`), Dr.Web (`drweb-configd`,
`/opt/drweb.com/bin/drweb-ctl`, `verified: true`, подтверждены на Ubuntu 24.04), KESL
(`kesl`, `/opt/kaspersky/kesl/bin/kesl-control`, `verified: false`).

Файл читает программа с правами root, поэтому в формате нет полей с командами и они
не добавляются: имена служб передаются в `systemctl` только отдельным аргументом через
`run_cmd`, пути проверяются только через `os.path.exists`.

Алгоритм загрузки (`load_products(path)`, выполняется один раз при старте `main.py`):
1. Прочитать файл как JSON (UTF-8) с `object_pairs_hook=OrderedDict`: в Python 3.5
   обычный словарь не сохраняет порядок полей, а от него зависит, какое неверное поле
   будет названо в сообщении первым. Ошибка чтения или синтаксиса → ошибка.
2. Корень — объект с единственным полем `products`, значение — список. Иначе → ошибка.
3. Взять следующий продукт. Он должен быть объектом.
4. Есть поле не из таблицы → ошибка «неизвестное поле» (так ловятся опечатки).
   Нет обязательного поля → ошибка.
5. Проверить типы полей по таблице. Имена служб в `services` должны
   полностью соответствовать `^[A-Za-z0-9][A-Za-z0-9@._-]*$`: имя не может начинаться
   с «-» и не будет принято `systemctl` за ключ. Пути в `files` начинаются с «/».
6. `id` уже встречался → ошибка.
7. Заполнить значения по умолчанию необязательных полей, добавить продукт в список.
8. Продукты закончились? Нет → шаг 3. Да → вернуть список.

Любая ошибка — `ValueError` с текстом «путь: продукт №N (id=…): что не так», например
`products.json: продукт №3 (id=kesl): неизвестное поле "servises"`. `main.py` выводит
сообщение в stderr и завершается с кодом 2 без трассировки: с битым файлом программа
не запускается.

#### Проверка

Состояние службы: `systemctl show -p LoadState -p ActiveState <имя>` (через `run_cmd`).
Вывод — строки «ключ=значение»: `LoadState=not-found` → служба не установлена;
`ActiveState=active` → запущена; иначе → установлена, но остановлена. Команда
не выполнилась → «состояние неизвестно» (служба не считается установленной).
`systemctl is-active` не подходит: про несуществующую и остановленную службу он одинаково
отвечает `inactive`. `# TODO(стенд)`: подтвердить формат вывода на стенде.

Настройки: секция `presence` — `cmd_timeout_s` (таймаут каждой команды `systemctl`).

Алгоритм `run(cfg, products)`:
1. Взять следующий продукт из списка `products`.
2. Проверить файлы из `files` (`os.path.exists`) и состояние служб из `services`.
   Продукт найден, если есть хотя бы один файл или установлена хотя бы одна служба.
3. Найден → добавить название в список АВ и/или МЭ по `kinds` (продукт с двумя видами
   попадает в оба). Если у продукта есть установленные службы, но ни одна не запущена, —
   после названия «(служба остановлена)». Подробности: «<название>: файл …; служба …
   запущена/остановлена». Пометки о `verified` у найденного продукта нет: раз он найден,
   его имена подтвердились на этой системе.
4. Не найден → если `verified` ложно, в подробности «<название>: не найден (профиль
   не проверен на стенде)»: продукт мог не найтись из-за неверных имён служб и путей.
5. Продукты закончились? Нет → шаг 1.
6. Итог и краткие строки «Антивирус:          <названия через запятую или «не найден»>»
   и «Межсетевой экран:   <…>»:
   - найдены и АВ, и МЭ → `OK` «найдены»;
   - найден только АВ → `WARNING` «найден только антивирус»;
   - найден только МЭ → `WARNING` «найден только межсетевой экран»;
   - ничего → `FAIL` «не найдены».

Подсказок у M2 нет.

### M3. Работоспособность МЭ (`check_firewall.py`)

Отвечает на вопрос: блокирует ли МЭ соединение, запрещённое тестовым правилом.

Подход методички «обратиться к запрещённому ресурсу» в России ненадёжен: зарубежный ресурс
может быть заблокирован провайдером, и программа ошибочно решит, что МЭ работает. Поэтому
используется один узел и два порта: контрольный (разрешён) и тестовый (запрещён правилом,
созданным проверяющим заранее). Имя разрешается один раз, оба подключения идут на один IP,
отличается только порт. Провайдерскую блокировку по IP это исключает.

Если запрещающих правил в netfilter нет совсем, МЭ пропускает весь трафик и проверять
нечего (например, ufw выключен: `ufw deny` при этом отвечает «Rules updated», но правило
не применяется). Поэтому перед подключениями M3 проверяет правила netfilter
(`check_netfilter`, ниже). Без root правила не читаются.

Настройки: секция `firewall_test` — `host`, `control_port`, `test_port`, `timeout_s`
(таймаут подключения и каждой команды `nft`/`iptables`).

Алгоритм (N — `test_port`):
1. `check_netfilter(timeout_s)`.
   - Правила прочитаны, запрещающих нет → `INCONCLUSIVE` «не определена — запрещающих
     правил нет», подсказка «Создайте тестовое правило и включите МЭ (README, «Тестовое
     правило»)». Подключения не выполняются.
   - Не прочитан ни один источник (нет root) → продолжить, в подробностях «Наличие
     запрещающих правил не проверено: правила netfilter не прочитаны» и причины.
   - Запрещающие правила есть → продолжить.
2. Разрешить имя `host` в IPv4 (`socket.getaddrinfo(..., AF_INET)`). Ошибка →
   `INCONCLUSIVE` «не определена — имя узла <host> не разрешается (DNS)».
3. Подключиться к `IP:control_port`. Не удалось → `INCONCLUSIVE` «не определена —
   контрольный узел недоступен».
4. Подключиться к `IP:test_port`.
5. Соединение установлено → `FAIL` «соединение на запрещённый порт N не заблокировано»,
   подсказка «Проверьте, что правило создано и МЭ включён (README, «Тестовое правило»)».
6. Не установлено → `OK` «соединение на запрещённый порт N заблокировано».
7. Тип отказа (в подробности):
   - `PermissionError` (EPERM) — «соединение запрещено локальным МЭ»: ядро сразу
     возвращает EPERM, когда исходящий пакет отброшен netfilter (`# TODO(стенд)`);
   - `ConnectionRefusedError` — «соединение отклонено (правило REJECT)»;
   - `socket.timeout` — «соединение не установлено за N с (вероятно, правило DROP)»
     и пометка, что таймаут косвенно указывает на МЭ, так как контрольный порт доступен;
   - другая ошибка — её текст.

Подробности (только `-v`): вывод `check_netfilter` (включая найденные запрещающие строки),
узел и IP, контрольный порт и время, тестовый порт, время и тип отказа.

Команды создания и удаления тестового правила (ufw, nftables) — в README.md.

#### Проверка фильтрации netfilter (`check_netfilter`)

Возвращает `(фильтрация, подробности, прочитан ли хоть один источник)`.

Запрещающими считаются только действия правил и политики цепочек. Простой поиск слов
drop/reject в тексте не годится: имена цепочек ufw (`-N ufw-reject-output`,
`chain ufw-reject-input {`) есть и при выключенном ufw.

| Источник | Шаблоны запрещающей строки (`re.search` по каждой строке) |
|---|---|
| `iptables -S`, `iptables-legacy -S` (с учётом регистра) | `^-P\s+(INPUT\|OUTPUT\|FORWARD)\s+DROP\b` — политика DROP; `\s-j\s+(DROP\|REJECT)\b` — действие правила |
| `nft list ruleset` (без учёта регистра) | `\bpolicy\s+drop\b` — политика; `(^\|\s)(drop\|reject)(\s\|;\|$)` — действие отдельным словом, а не часть имени |

Примеры. Срабатывают: `-P OUTPUT DROP`, `-A ufw-user-output -p tcp --dport 80 -j DROP`,
`-A ufw-reject-output -j REJECT`, `tcp dport 80 counter drop`, `policy drop;`,
`reject with icmp type port-unreachable`. Не срабатывают: `-N ufw-reject-output`,
`-A ufw-after-output -j ufw-reject-output`, `chain ufw-reject-input {`,
`jump ufw-reject-output`, `-P OUTPUT ACCEPT`.

Алгоритм:
1. Взять следующую команду: `nft list ruleset`, `iptables -S`, `iptables-legacy -S`.
2. Для `iptables-legacy -S`: выполнять, только если `iptables -V` сообщает `(legacy)` или
   модуль `ip_tables` уже загружен (строка `ip_tables` в `/proc/modules`). Иначе
   пропустить с пометкой «legacy-таблицы не используются»: сам вызов загрузил бы модуль
   и создал таблицы в ядре, а программа ничего не меняет в системе.
3. Утилиты нет или команда завершилась с ошибкой (без root) — пропустить, причину
   записать в подробности.
4. Проверить каждую строку вывода по шаблонам своего источника, найденные строки
   запомнить. В подробности: «<команда>: запрещающих правил: N» или «…: запрещающих
   правил нет».
5. Команды закончились? Нет → шаг 1.
6. Фильтрация включена, если найдена хотя бы одна запрещающая строка. В подробности —
   найденные строки с именем команды, не больше 5 (обрезаются по ширине вывода).

### M4. Работоспособность АВ (`check_antivirus.py`)

Отвечает на вопрос: реагирует ли резидентная защита (on-access) на создание тестового
файла EICAR.

Настройки: секция `antivirus_test` — `eicar_dir`, `eicar_timeout_s`, `poll_interval_s`.
Константы модуля (не настройки): `FILE_NAME`, `EICAR_PARTS`.

Реакцией АВ считается только `PermissionError` (EACCES или EPERM) при записи или чтении
и исчезновение файла. Любая другая `OSError` (нет каталога, нет места на диске) — это
не реакция АВ, а `ERROR` «ошибка проверки (<что делали>: <текст ошибки>)».

Алгоритм (T — `eicar_timeout_s`, N — секунды от начала записи):
1. Собрать строку EICAR из частей, хранящихся в коде раздельно (никогда целиком).
2. Создать собственный подкаталог `tempfile.mkdtemp(prefix="seccheck_", dir=eicar_dir)`:
   внутри `eicar_dir` или, если он `null`, в системном временном каталоге.
   `OSError` → `ERROR` «ошибка проверки (создание каталога: …)».
3. Записать `eicar_test.txt`: `open` → `write` → `flush` → `os.fsync` → `close`
   (многие АВ проверяют файл при закрытии после записи).
4. `PermissionError` при записи или закрытии → `OK` «тестовый файл обнаружен за N с
   (запись заблокирована)». Другой `OSError` → `ERROR` «ошибка проверки (запись
   тестового файла: …)».
5. Подождать `poll_interval_s`, напечатать прогресс `Ожидание реакции АВ… 12/30 с`
   (через `\r`, только если вывод — терминал).
6. Файл не существует → `OK` «тестовый файл обнаружен за N с (файл удалён)».
7. Попробовать прочитать файл. `PermissionError` → `OK` «тестовый файл обнаружен за N с
   (доступ к файлу заблокирован)»; файл исчез → как шаг 6; другой `OSError` → `ERROR`
   «ошибка проверки (чтение тестового файла: …)».
8. Прошло меньше T → шаг 5.
9. Иначе → `FAIL` «тестовый файл не обнаружен за T с».
10. В `finally` (в том числе после Ctrl+C): стереть строку прогресса, удалить свой файл
    и свой подкаталог (`os.remove`, `os.rmdir`); сам `eicar_dir` и всё прочее в нём
    не трогать. Если удаление не удалось — краткая строка «Внимание: не удалось удалить
    <путь>: …»: она печатается всегда, без `-v`, потому что на диске остался тестовый файл.
11. При `FAIL` подсказка «Проверьте, что включена постоянная защита (для ClamAV —
    clamonacc)».

Подробности (только `-v`): путь к файлу, результат удаления файла программой; при `FAIL` —
подсказки для ClamAV: каталог, в котором создан подкаталог (`eicar_dir` или системный
временный), должен входить в `OnAccessIncludePath`, блокировка работает только при
`OnAccessPrevention yes`, служба clamonacc должна быть запущена.

### M5. Меню и отчёт (`main.py`)

Результаты хранятся в словаре `results`: идентификатор проверки → `(статус, краткие,
подробности)`.

Алгоритм работы программы:
1. `sys.dont_write_bytecode = True` до импорта модулей проекта (при запуске через `sudo`
   не создаются каталоги `__pycache__` с владельцем root). Сразу после этого: если
   кодировка `sys.stdout` или `sys.stderr` не UTF-8 (локаль C/POSIX), заменить поток на
   `io.TextIOWrapper(поток.buffer, encoding="utf-8", errors="replace",
   line_buffering=True)`; иначе первый вывод кириллицы завершится `UnicodeEncodeError`.
2. Разобрать аргументы (`--help`, `--version`, `--config PATH`, `--products PATH`,
   `-v`/`--verbose` — подробный вывод).
3. Загрузить настройки: `load_config` (раздел 6) из файла `--config` или из
   `/etc/seccheck/config.json`. Ошибка → сообщение в stderr, выход с кодом 2.
   Затем загрузить список продуктов: `load_products` (раздел M2) из файла `--products`
   или из `products.json` рядом с `main.py`. Ошибка → сообщение в stderr, выход с кодом 2.
4. Напечатать заголовок: название, версия, ОС, запуск от root да/нет. Без root —
   предупреждение одной строкой: «Ограничена проверка M3: правила МЭ не будут прочитаны».
5. Показать меню (названия пунктов 1–4 берутся из `CHECKS`), прочитать пункт.
6. 1–4 → выполнить проверку, записать в `results`, напечатать результат (раздел 4):
   итог, краткие строки, с `-v` — подробности. Исключение в модуле → `ERROR`
   «ошибка проверки (…)», программа продолжает работу.
7. 5 → выполнить M1–M4 по порядку.
8. 6 → вывести отчёт (ниже).
9. 0 или конец ввода → выход с кодом 0. Иначе → шаг 5.
10. Ctrl+C в любой момент → «Прервано пользователем», код 130 (файл EICAR удаляется
   блоком `finally` в M4).

Отчёт:
1. Заголовок: «Результаты тестирования средств защиты», название и версия, дата и время,
   имя ПК, ОС (`os_info()`), версия Python, запуск от root да/нет, использованные файлы
   настроек и продуктов (абсолютные пути).
2. Для M1–M4 по порядку — результат в том же виде, что при запуске проверки: итог,
   краткие строки, с `-v` — подробности. Проверки нет в `results` → `NOT_RUN`
   «<Название>: не выполнялась».

Метки статусов: `[  OK  ]`, `[ WARN ]`, `[ FAIL ]`, `[  ??  ]` (INCONCLUSIVE),
`[ ---- ]` (NOT_RUN), `[ ERR  ]`. Ширина вывода до 100 символов: результаты пойдут
на скриншоты в записку.

Меню:

```
SecCheck 0.1 · Debian GNU/Linux 12 (bookworm) · запуск от root: да

  1  Подключение к интернету
  2  Наличие АВ и МЭ
  3  Работоспособность МЭ
  4  Работоспособность АВ
  5  Выполнить все проверки
  6  Вывести отчёт
  0  Выход

Выберите пункт: _
```

## 8. Установка (`install.sh`, `uninstall.sh`)

- Первая строка `main.py`: `#!/usr/bin/env python3` (для запуска `sudo ./main.py`).
- `install.sh` (через `sudo`): проверить root; удалить старый `/opt/seccheck`;
  скопировать `*.py`, `products.json` и образец `config.json` в `/opt/seccheck` (владелец
  root:root, каталог 755, файлы 644);
  создать `/usr/local/bin/seccheck` — sh-обёртку
  `exec /usr/bin/python3 /opt/seccheck/main.py "$@"` с правами 755. Повторный запуск —
  обновление.
- Настройки: создать `/etc/seccheck` (root, 755). Если `/etc/seccheck/config.json` нет —
  скопировать туда `config.json` проекта (root, 644). Существующий файл никогда
  не перезаписывается: он проверяется установленным `common.load_config`, и при ошибках
  (например, в новой версии появился ключ) скрипт выводит их, напоминает сравнить файл
  с `/opt/seccheck/config.json` и после завершения установки выходит с кодом 1.
- `uninstall.sh`: удалить `/opt/seccheck` и `/usr/local/bin/seccheck`. `/etc/seccheck`
  не удалять, а напечатать, что настройки сохранены, и команду `sudo rm -r /etc/seccheck`.
- Почему каталог доступен на запись только root: программа работает от root, и если бы
  её код мог изменить обычный пользователь, это было бы повышением привилегий (README.md).

## 10. Проверка перед сдачей

- `vermin -q -t=3.5- --no-tips --violations .` — пустой вывод (vermin ставится только
  в среду разработки).
- `python3 -m py_compile` для каждого `.py` (проверяет только синтаксис той версии,
  которой запущен; на стенде — 3.5). При наличии Docker:
  `docker run --rm -v "$PWD":/src -w /src python:3.5 python -m py_compile *.py`.
- Строка EICAR целиком не встречается ни в одном файле проекта.
- `config.json` проходит `load_config`, `products.json` — `load_products`, в том числе
  при `LC_ALL=C LANG=C`; `LC_ALL=C LANG=C python3 main.py --help` выводит кириллицу
  без ошибок.
- Ручной запуск на стенде: все четыре проверки и отчёт (с `-v` и без), запуск без root,
  Ctrl+C во время M4.

## 11. Критерии готовности

- `sudo seccheck` на стенде выполняет все проверки и выводит отчёт.
- Без root программа не падает и в отчёте объясняет, что ограничено.
- Ни одна внешняя команда не может повесить программу (таймауты везде).
- Строка EICAR целиком не встречается в исходниках; тестовый файл удаляется даже после
  Ctrl+C.
- Код работает на Python 3.5.
- Код каждого модуля проверок соответствует пошаговому алгоритму из раздела 7.

## 12. Известные ограничения (для раздела «Анализ результатов»)

- Обнаружение продуктов зависит от полноты и точности `products.json`. M2 отвечает только
  на вопрос о наличии: найденный продукт может быть выключен (служба ufw в Ubuntu
  запущена и при выключенном ufw); работу МЭ и АВ проверяют M3 и M4.
- Фильтрация определяется по действиям DROP/REJECT и политикам DROP в правилах (M3,
  `check_netfilter`). Проверка учитывает правила всех направлений, поэтому запрещающие
  правила, не связанные с исходящим трафиком (например, правила Docker в FORWARD), могут
  дать в M3 `FAIL` вместо `INCONCLUSIVE`. Правила netfilter общие для системы, поэтому
  по ним нельзя сказать, какой продукт их создал.
- Слово `drop` или `reject` в комментарии правила nft (`comment "drop ssh"`) будет
  принято за действие.
- Правила iptables-legacy проверяются, только если `iptables -V` сообщает `(legacy)` или
  в `/proc/modules` есть `ip_tables`. Если `ip_tables` встроен в ядро, а не загружен
  модулем, legacy-правила при nft-варианте `iptables` не проверяются.
- Фильтры на eBPF/XDP работают в обход netfilter и правилами nft не видны.
- M3 проверяет одно правило на исходящий трафик, а не всю политику МЭ.
- M4 проверяет реакцию резидентного модуля на эталонный тестовый файл, а не способность
  обнаруживать реальные угрозы.
- Решение M1 основано на доступности выбранных узлов; на точность влияют блокировки
  и режим белых списков.
