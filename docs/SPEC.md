# SecCheck — техническое задание

## 0. Контекст

Курсовая работа «Методы и средства защиты информации в компьютерных сетях», МТУСИ.
По методичке программа должна содержать пять модулей:

1. проверка наличия подключения к интернету;
2. проверка наличия установленных межсетевого экрана (МЭ) и антивируса (АВ);
3. проверка работоспособности МЭ;
4. проверка работоспособности АВ (тестовый файл EICAR);
5. вывод результатов.

Методичка разрешает консольный интерфейс. Примеры в ней на C# под Windows: мы их не копируем,
но покрываем те же функции. Кроме кода нужны блок-схемы всех алгоритмов (ГОСТ 19.701-90).
Поэтому алгоритмы ниже записаны пошагово, и код обязан им соответствовать.

## 1. Область работ

- Linux с systemd (Debian, Ubuntu, Astra Linux и подобные). Логики под конкретный
  дистрибутив нет.
- Только консольный интерфейс: интерактивное меню. Флаги командной строки: `--help`,
  `--version`, `--products PATH`.
- Python 3.7+ (чтобы работало и на старых дистрибутивах), только стандартная библиотека.

## 2. Стенд

- Виртуальная машина с Linux на systemd.
- Запуск программы от root (`sudo`). Без root проверка M2 не может прочитать правила МЭ.
- Средства защиты на стенде: ClamAV с `clamonacc` (проверка при доступе) и `ufw`.
  Опционально Dr.Web для Linux или Kaspersky Endpoint Security для Linux (KESL).
- Тестовое правило МЭ автор создаёт вручную по командам из README.md.

## 3. Структура проекта

```
seccheck/

├── common.py           # run_cmd(), is_root(), os_info(), константы статусов

├── check_presence.py   # M2 + загрузка и проверка списка продуктов
├── products.json       # список продуктов для M2
├── check_firewall.py   # M3
├── check_antivirus.py  # M4
├── install.sh          # установка в /opt/seccheck и команда seccheck

├── CLAUDE.md

```

Каждый модуль проверки содержит функцию `run()` и свои настройки — константы ЗАГЛАВНЫМИ
буквами в начале файла. Модули могут сами печатать (прогресс ожидания в M4). Исключение —
M2: `run(products)` получает список продуктов, загруженный при старте из `products.json`.

## 4. Статусы и формат результата

Статусы — строковые константы в `common.py`:

| Константа | Смысл |
|---|---|
| `OK` | проверка пройдена |
| `WARNING` | работает частично / есть замечания |
| `FAIL` | средство защиты не сработало / отсутствует |
| `INCONCLUSIVE` | вывод сделать нельзя (нет сети, недоступна цель) |
| `NOT_RUN` | проверку не запускали |
| `ERROR` | сбой программы или нехватка прав |

`run()` возвращает кортеж `(статус, строки)`. `строки[0]` — краткий итог в одну строку,
остальные — подробности.

## 5. Общие функции (`common.py`)

| Функция | Как работает |
|---|---|
| `run_cmd(cmd, timeout)` | `subprocess.run(cmd, stdout=PIPE, stderr=PIPE, universal_newlines=True, errors="replace", timeout=…, env=окружение + LC_ALL=C)`, без `shell=True`. Возвращает `(код, stdout, stderr)`. `FileNotFoundError` → код `CMD_NOT_FOUND` (−1), `TimeoutExpired` → `CMD_TIMEOUT` (−2) |
| `is_root()` | `os.geteuid() == 0` |
| `os_info()` | значение `PRETTY_NAME` из `/etc/os-release`; если его нет — «Linux». Только для заголовка отчёта |

`LC_ALL=C` нужен потому, что вывод `systemctl`, `iptables` и других утилит локализован,
а программа разбирает только английский.

## 6. Модули проверок

### M1. Проверка подключения к интернету (`check_network.py`)

Узлы делятся на две группы, чтобы отличить полный доступ от ограниченного (белые списки
мобильных операторов, блокировки). ICMP часто режется, поэтому решение принимается по TCP.

Константы: `RU_HOSTS`, `FOREIGN_HOSTS`, `TCP_PORT` (443), `TCP_TIMEOUT` (3 с),
`PING_TIMEOUT` (2 с).

Алгоритм:
1. Составить список узлов из групп `RU_HOSTS` и `FOREIGN_HOSTS`.
2. Для каждого узла: `ping -c 1 -W PING_TIMEOUT` через `run_cmd` (результат только
   для сведения).
3. Для того же узла: TCP-подключение к `TCP_PORT` с таймаутом `TCP_TIMEOUT`
   (`socket.create_connection`). Ошибку DNS (`socket.gaierror`) запомнить отдельно.
4. Группа доступна, если хотя бы один её узел ответил по TCP.
5. Ни одна группа не доступна → `FAIL` «Нет подключения к интернету». Если у всех узлов
   ошибка DNS, добавить в подробности «Не работает разрешение имён (DNS)».
6. Доступна одна группа → `WARNING` «Доступ к интернету ограничен: доступны только
   российские / только зарубежные узлы».
7. Доступны обе → `OK` «Подключение к интернету есть».
8. В подробностях по каждому узлу: ICMP да/нет, TCP да/нет, время подключения в мс.
   Если TCP работает, а ICMP нет ни у одного узла, добавить «ICMP блокируется».

Подключения выполняются последовательно (так проще объяснить).

### M2. Обнаружение МЭ и АВ (`check_presence.py`)

В Linux нет единого реестра средств защиты (как Центр безопасности Windows), поэтому:
(а) поиск известных продуктов по службам systemd и файлам;
(б) универсальная проверка: есть ли запрещающие правила в netfilter, через который работают
практически все сетевые фильтры Linux.

Уровни продукта (константы модуля): `NOT_FOUND` «не найден», `INSTALLED` «установлен»,
`RUNNING` «работает», `ACTIVE` «защита активна».

#### Файл продуктов `products.json`

Список продуктов хранится во внешнем файле. По умолчанию это `products.json` в каталоге,
где лежит `main.py` (`os.path.dirname(os.path.realpath(__file__))`); флаг
`--products PATH` задаёт другой файл. Формат: `{"products": [ {...}, ... ]}`.

| Поле | Обяз. | Тип | Смысл |
|---|---|---|---|
| `id` | да | непустая строка, уникальна | идентификатор |
| `name` | да | непустая строка | название для отчёта |
| `kinds` | да | непустой список из `"antivirus"`, `"firewall"` | вид продукта |
| `services` | да | список имён служб (может быть пустым) | любая активна → `RUNNING` |
| `files` | да | список абсолютных путей (может быть пустым) | любой существует → `INSTALLED` |
| `protection_service` | нет | имя службы или `null` (по умолчанию) | активна → `ACTIVE` |
| `active_if_filtering` | нет | bool, по умолчанию `false` | `ACTIVE`, если уровень `RUNNING` и netfilter фильтрует |
| `verified` | нет | bool, по умолчанию `false` | профиль проверен на стенде |
| `notes` | нет | строка | примечание, в отчёт не выводится |

`active_if_filtering` нужен МЭ без отдельной службы защиты (ufw): его служба лишь загружает
правила, а признаком работающей защиты служит наличие запрещающих правил в netfilter.
Без `protection_service` и `active_if_filtering` высший уровень продукта — `RUNNING`.

Продукты в поставке: ClamAV (`clamav-daemon`, `/usr/sbin/clamd`, служба защиты
`clamav-clamonacc`, `verified: false`), ufw (`ufw`, `/usr/sbin/ufw`,
`active_if_filtering: true`, `verified: true`), Dr.Web (`drweb-configd`,
`/opt/drweb.com/bin/drweb-ctl`, `verified: false`), KESL (`kesl`,
`/opt/kaspersky/kesl/bin/kesl-control`, `verified: false`).

Файл читает программа с правами root, поэтому в формате нет полей с командами и они
не добавляются: имена служб передаются в `systemctl` только отдельным аргументом через
`run_cmd`, пути проверяются только через `os.path.exists`.

Алгоритм загрузки (`load_products(path)`, выполняется один раз при старте `main.py`):
1. Прочитать файл как JSON (UTF-8). Ошибка чтения или синтаксиса → ошибка.
2. Корень — объект с единственным полем `products`, значение — список. Иначе → ошибка.
3. Взять следующий продукт. Он должен быть объектом.
4. Есть поле не из таблицы → ошибка «неизвестное поле» (так ловятся опечатки).
   Нет обязательного поля → ошибка.
5. Проверить типы полей по таблице. Имена служб (`services`, `protection_service`) должны
   полностью соответствовать `^[A-Za-z0-9][A-Za-z0-9@._-]*$`: имя не может начинаться
   с «-» и не будет принято `systemctl` за ключ. Пути в `files` начинаются с «/».
6. `id` уже встречался → ошибка.
7. Заполнить значения по умолчанию необязательных полей, добавить продукт в список.
8. Продукты закончились? Нет → шаг 3. Да → вернуть список.

Любая ошибка — `ValueError` с текстом «путь: продукт №N (id=…): что не так», например
`products.json: продукт №3 (id=kesl): неизвестное поле "servises"`. `main.py` выводит
сообщение в stderr и завершается с кодом 2 без трассировки: с битым файлом программа
не запускается.

#### Проверка

Состояние службы: `systemctl is-active <имя>`, активна, если код 0 и вывод `active`.

Алгоритм `run(products)`:
1. Netfilter (проверяется первым, от него зависит уровень МЭ): выполнить
   `nft list ruleset`, `iptables -S`, `iptables-legacy -S`. Если в выводе любой успешно
   выполненной команды есть `drop` или `reject` (без учёта регистра) — фильтрация
   включена. Утилиты нет — пропустить. Без root ни одна команда не выполнится →
   в подробности «Правила МЭ не прочитаны: нужны права root».
2. Взять следующий продукт из списка `products`.
3. Есть хотя бы один файл из `files` → `INSTALLED`; активна хотя бы одна служба
   из `services` → `RUNNING`.
4. Признаков нет → перейти к шагу 6.
5. Определить активность защиты: активна `protection_service` → `ACTIVE`; либо
   `active_if_filtering`, уровень `RUNNING` и netfilter фильтрует → `ACTIVE`. Добавить
   продукт с уровнем и признаками в список найденных; если `verified` ложно, в строке
   подробностей пометка «(профиль не проверен на стенде)».
6. Продукты закончились? Нет → шаг 2.
7. Итоговый статус:
   - есть АВ с `ACTIVE` и (МЭ с `ACTIVE` или фильтрация включена) → `OK`;
   - не найдено ни АВ, ни МЭ, фильтрации нет → `FAIL`;
   - иначе → `WARNING` с перечислением, чего не хватает.

### M3. Проверка работоспособности МЭ (`check_firewall.py`)

Подход методички «обратиться к запрещённому ресурсу» в России ненадёжен: зарубежный ресурс
может быть заблокирован провайдером, и программа ошибочно решит, что МЭ работает. Поэтому
используется один узел и два порта: контрольный (разрешён) и тестовый (запрещён правилом,
созданным проверяющим заранее). Имя разрешается один раз, оба подключения идут на один IP,
отличается только порт. Провайдерскую блокировку по IP это исключает. M3 не зависит от M2.

Константы: `FW_HOST` (`ya.ru`), `CONTROL_PORT` (443), `TEST_PORT` (80), `TIMEOUT` (3 с).

Алгоритм:
1. Разрешить имя `FW_HOST` в IPv4 (`socket.getaddrinfo(..., AF_INET)`).
   Ошибка → `INCONCLUSIVE` «Не удалось разрешить имя».
2. Подключиться к `IP:CONTROL_PORT`. Не удалось → `INCONCLUSIVE`
   «Контрольная цель недоступна, вывод о работе МЭ сделать нельзя».
3. Подключиться к `IP:TEST_PORT`.
4. Соединение установлено → `FAIL` «МЭ пропустил соединение, которое должен был запретить.
   Правило не создано или МЭ не работает» + подсказка про README.
5. Не установлено → `OK` «МЭ работает».
6. В подробностях тип отказа:
   - `PermissionError` (EPERM) — «соединение запрещено локальным МЭ»: ядро сразу
     возвращает EPERM, когда исходящий пакет отброшен netfilter (`# TODO(стенд)`);
   - `ConnectionRefusedError` — «соединение отклонено (правило REJECT)»;
   - `socket.timeout` — «соединение не установлено за N с (вероятно, правило DROP)»
     и пометка, что таймаут косвенно указывает на МЭ, так как контрольный порт доступен;
   - другая ошибка — её текст.

   Также в подробностях: IP, порты, время подключений.

Команды создания и удаления тестового правила (ufw, nftables) — в README.md.

### M4. Проверка работоспособности АВ (`check_antivirus.py`)

Резидентная защита (on-access) должна среагировать на создание тестового файла EICAR.

Константы: `EICAR_TIMEOUT` (30 с), `POLL_INTERVAL` (1 с), `FILE_NAME`, `EICAR_PARTS`.

Алгоритм:
1. Собрать строку EICAR из частей, хранящихся в коде раздельно (никогда целиком).
2. Создать временный каталог `tempfile.mkdtemp(prefix="seccheck_")`.
3. Записать `eicar_test.txt`: `open` → `write` → `flush` → `os.fsync` → `close`
   (многие АВ проверяют файл при закрытии после записи).
4. `PermissionError` при записи или закрытии → `OK` «запись тестового файла
   заблокирована». Другой `OSError` (нет места и т. п.) → `ERROR`: это не реакция АВ.
5. Подождать `POLL_INTERVAL`, напечатать прогресс `Ожидание реакции АВ… 12/30 с`
   (через `\r`, только если вывод — терминал).
6. Файл не существует → `OK` «файл удалён или помещён в карантин через N с».
7. Попробовать прочитать файл. `PermissionError` → `OK` «доступ к файлу заблокирован».
8. Прошло меньше `EICAR_TIMEOUT` → шаг 5.
9. Иначе → `FAIL` «Резидентная защита не среагировала за T с».
10. В `finally` (в том числе после Ctrl+C): стереть строку прогресса, удалить файл
    и каталог; если удаление не удалось — предупреждение в подробностях с путём.
11. В подробностях: путь к файлу; при `FAIL` — подсказки для ClamAV: временный каталог
    должен входить в `OnAccessIncludePath`, блокировка работает только при
    `OnAccessPrevention yes`, служба clamonacc должна быть запущена.

### M5. Меню и отчёт (`main.py`)

Результаты хранятся в словаре `results`: идентификатор проверки → `(статус, строки)`.

Алгоритм работы программы:
1. `sys.dont_write_bytecode = True` до импорта модулей проекта (при запуске через `sudo`
   не создаются каталоги `__pycache__` с владельцем root).
2. Разобрать аргументы (`--help`, `--version`, `--products PATH`).
3. Загрузить список продуктов: `load_products` (раздел M2) из файла `--products` или из
   `products.json` рядом с `main.py`. Ошибка → сообщение в stderr, выход с кодом 2.
4. Напечатать заголовок: название, версия, ОС, запуск от root да/нет. Без root —
   предупреждение одной строкой: «Ограничена проверка M2: правила МЭ не будут прочитаны».
5. Показать меню, прочитать пункт.
6. 1–4 → выполнить проверку, записать в `results`, напечатать результат.
   Исключение в модуле → статус `ERROR` с текстом исключения, программа продолжает работу.
7. 5 → выполнить M1–M4 по порядку.
8. 6 → вывести отчёт (ниже).
9. 0 или конец ввода → выход с кодом 0. Иначе → шаг 5.
10. Ctrl+C в любой момент → «Прервано пользователем», код 130 (файл EICAR удаляется
   блоком `finally` в M4).

Отчёт:
1. Заголовок: «Результаты тестирования средств защиты», название и версия, дата и время,
   имя ПК, ОС (`os_info()`), версия Python, запуск от root да/нет, использованный файл
   продуктов (абсолютный путь).
2. Для M1–M4 по порядку: если проверки нет в `results` — статус `NOT_RUN`
   и текст «<название>: не выполнялась». Строка: номер, метка статуса, итог.
3. Раздел «Подробности»: для каждой проверки итог и все строки подробностей.

Метки статусов: `[  OK  ]`, `[ WARN ]`, `[ FAIL ]`, `[  ??  ]` (INCONCLUSIVE),
`[ ---- ]` (NOT_RUN), `[ ERR  ]`. Ширина вывода до 100 символов: результаты пойдут
на скриншоты в записку.

Меню:

```
SecCheck 0.1 · Debian GNU/Linux 12 (bookworm) · запуск от root: да

  1  Проверка подключения к интернету
  2  Проверка наличия МЭ и АВ
  3  Проверка работоспособности МЭ
  4  Проверка работоспособности АВ
  5  Выполнить все проверки
  6  Вывести отчёт
  0  Выход

Выберите пункт: _
```

## 7. Установка (`install.sh`, `uninstall.sh`)

- Первая строка `main.py`: `#!/usr/bin/env python3` (для запуска `sudo ./main.py`).
- `install.sh` (через `sudo`): проверить root; удалить старый `/opt/seccheck`;
  скопировать `*.py` и `products.json` в `/opt/seccheck` (владелец root:root, каталог 755,
  файлы 644);
  создать `/usr/local/bin/seccheck` — sh-обёртку
  `exec /usr/bin/python3 /opt/seccheck/main.py "$@"` с правами 755. Повторный запуск —
  обновление.
- `uninstall.sh`: удалить `/opt/seccheck` и `/usr/local/bin/seccheck`.
- Почему каталог доступен на запись только root: программа работает от root, и если бы
  её код мог изменить обычный пользователь, это было бы повышением привилегий (README.md).

## 9. Проверка перед сдачей

- `python3 -m py_compile` для каждого `.py`.
- Разбор каждого файла грамматикой Python 3.7: `ast.parse(..., feature_version=(3, 7))`
  (`py_compile` проверяет только синтаксис той версии, которой запущен).
- Строка EICAR целиком не встречается ни в одном файле проекта.
- Ручной запуск на стенде: все четыре проверки и отчёт, запуск без root, Ctrl+C во время M4.

## 10. Критерии готовности

- `sudo seccheck` на стенде выполняет все проверки и выводит отчёт.
- Без root программа не падает и в отчёте объясняет, что ограничено.
- Ни одна внешняя команда не может повесить программу (таймауты везде).
- Строка EICAR целиком не встречается в исходниках; тестовый файл удаляется даже после
  Ctrl+C.
- Код работает на Python 3.7.
- Код каждого модуля проверок соответствует пошаговому алгоритму из раздела 6.

## 11. Известные ограничения (для раздела «Анализ результатов»)

- Обнаружение продуктов зависит от полноты и точности `products.json`; проверка netfilter
  показывает, есть ли фильтрация, но не называет продукт.
- Фильтрация netfilter общая для всей системы, поэтому её наличие не доказывает, что
  правила создал именно этот продукт (`active_if_filtering`): уровень «защита активна»
  у ufw может быть получен за счёт правил другой программы.
- Фильтрация определяется поиском слов drop/reject в выводе правил. Запрещающие правила,
  не связанные со средством защиты (например, правила Docker), дадут положительный ответ.
- Фильтры на eBPF/XDP работают в обход netfilter и правилами nft не видны.
- M3 проверяет одно правило на исходящий трафик, а не всю политику МЭ.
- M4 проверяет реакцию резидентного модуля на эталонный тестовый файл, а не способность
  обнаруживать реальные угрозы.
- Решение M1 основано на доступности выбранных узлов; на точность влияют блокировки
  и режим белых списков.
