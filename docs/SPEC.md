# SecCheck — техническое задание

## 0. Контекст

Курсовая работа «Методы и средства защиты информации в компьютерных сетях», МТУСИ.
По методичке программа должна содержать пять модулей:

1. проверка наличия подключения к интернету;
2. проверка наличия установленных межсетевого экрана (МЭ) и антивируса (АВ);
3. проверка работоспособности МЭ;
4. проверка работоспособности АВ (тестовый файл EICAR);
5. вывод результатов.

Методичка разрешает консольный интерфейс. Примеры в ней на C# под Windows: мы их не копируем,
но покрываем те же функции. Кроме кода нужны блок-схемы всех алгоритмов (ГОСТ 19.701-90).
Поэтому алгоритмы ниже записаны пошагово, и код обязан им соответствовать.

## 1. Область работ

- Linux с systemd (Debian, Ubuntu, Astra Linux и подобные). Логики под конкретный
  дистрибутив нет.
- Только консольный интерфейс: интерактивное меню. Флаги командной строки: `--help`,
  `--version`, `-v`/`--verbose`. Пути к файлам постоянные: настройки —
  `/etc/seccheck/config.json`, список продуктов — `products.json` рядом с `main.py`.
- Python 3.5+ (на стенде 3.5; чтобы работало и на старых дистрибутивах), только стандартная
  библиотека. Совместимость проверяется инструментом vermin (раздел 10).
- Кодировка везде UTF-8 явно: в 3.5 при локали C/POSIX (sudo, cron, ssh с `LANG=C`)
  кодировка по умолчанию — ASCII. Текстовые файлы открываются с `encoding="utf-8"`,
  вывод команд декодируется `run_cmd`, а `main.py` при старте переоткрывает `sys.stdout`
  и `sys.stderr` в UTF-8, если их кодировка другая (раздел 7, M5, шаг 1).

## 2. Стенд

- Виртуальная машина с Linux на systemd.
- Запуск программы от root (`sudo`). Без root проверка M3 не выполняется: тестовое
  правило МЭ может добавить только root.
- Средства защиты на стенде: ClamAV с `clamonacc` (проверка при доступе) и `ufw`.
  Опционально Dr.Web для Linux или Kaspersky Endpoint Security для Linux (KESL).
- Тестовое правило МЭ программа создаёт и удаляет сама (M3), от проверяющего ничего
  не требуется.

Каждый модуль проверки содержит функцию `run(cfg)`, где `cfg` — его секция файла настроек
(раздел 6). Значений настроек по умолчанию в коде нет. Модули могут сами печатать
(строку ожидания в M4). M2 и M3 дополнительно получают список продуктов:
`run(cfg, products)`.

## 4. Статусы и формат результата

Статусы — строковые константы в `common.py`:

| Константа | Смысл |
|---|---|
| `OK` | проверка пройдена |
| `WARNING` | работает частично / есть замечания |
| `FAIL` | средство защиты не сработало / отсутствует |
| `INCONCLUSIVE` | вывод сделать нельзя (нет сети, недоступна цель) |
| `NOT_RUN` | проверку не запускали |
| `ERROR` | сбой программы или нехватка прав |

Каждая проверка отвечает только на свой вопрос: M1 — есть ли интернет, M2 — есть ли АВ
и МЭ, M3 — блокирует ли МЭ запрещённое соединение, M4 — реагирует ли АВ на тестовый файл.
В вывод проверки попадает только то, что отвечает на её вопрос.

`run()` возвращает кортеж `(статус, краткие, подробности)`:
- `краткие[0]` — результат без названия проверки, например `"есть"`;
- `краткие[1:]` — строки, которые печатаются всегда: найденные продукты в M2, подсказки
  при не-OK («Проверьте…»), предупреждения о неудалённом файле в M4 и о неудалённом
  тестовом правиле в M3;
- `подробности` — печатаются только с флагом `-v`.

`main.py` печатает итог в виде `<метка> <id>  <Название>: <результат>`, под ним краткие
строки, с `-v` — подробности (отступ 9 пробелов). Название берётся из списка `CHECKS`
в `main.py` и одинаково в меню, в строке результата и в отчёте: M1 «Подключение
к интернету», M2 «Наличие АВ и МЭ», M3 «Работоспособность МЭ», M4 «Работоспособность АВ».
Исключение в модуле → `ERROR` «<Название>: ошибка проверки (<тип>: <текст>)».

## 5. Общие функции (`common.py`)

| Функция | Как работает |
|---|---|
| `run_cmd(cmd, timeout)` | `subprocess.run(cmd, stdout=PIPE, stderr=PIPE, timeout=…, env=окружение + LC_ALL=C + LANGUAGE=C)`, без `shell=True`. Вывод получается байтами и декодируется `decode("utf-8", "replace")`: текстовый режим декодировал бы по локали, а при `LANG=C` в 3.5 это ASCII. Возвращает `(код, stdout, stderr)`. `FileNotFoundError` → код `CMD_NOT_FOUND` (−1), `TimeoutExpired` → `CMD_TIMEOUT` (−2) |
| `is_root()` | `os.geteuid() == 0` |
| `os_info()` | значение `PRETTY_NAME` из `/etc/os-release`; если его нет — «Linux». Только для заголовка отчёта |
| `load_json(path)` | чтение JSON-файла в UTF-8 с `object_pairs_hook=OrderedDict`; любая ошибка чтения или разбора → `ValueError` «<путь>: файл не найден или не является корректным JSON» |
| `load_config(path)` | загрузка и проверка файла настроек (раздел 6) |

`LC_ALL=C` нужен потому, что вывод `systemctl`, `ufw` и других утилит локализован,
а программа разбирает только английский. `LANGUAGE=C` — для программ на Python (ufw):
модуль gettext смотрит `LANGUAGE` раньше `LC_ALL`.

## 6. Настройки (`config.json`)

Узлы, порты и таймауты проверок хранятся во внешнем JSON-файле. Файл обязателен:
значений по умолчанию в коде нет, без файла программа не запускается.

Файл всегда `/etc/seccheck/config.json` (`common.DEFAULT_CONFIG_PATH`).

`config.json` в репозитории — полный набор ключей с рабочими значениями. `install.sh`
копирует его в `/etc/seccheck/config.json` только при первой установке (раздел 8).

| Секция | Ключ | Тип и ограничения | Значение в репозитории |
|---|---|---|---|
| `network` | `ru_hosts` | непустой список имён узлов | `["ya.ru", "vk.com"]` |
| | `foreign_hosts` | непустой список имён узлов | `["example.com", "github.com"]` |
| | `tcp_port` | порт | 443 |
| | `tcp_timeout_s` | таймаут | 3 |
| `presence` | `cmd_timeout_s` | таймаут одной команды `systemctl` | 5 |
| `firewall_test` | `host` | имя узла | `"ya.ru"` |
| | `test_port` | порт, соединения на который запрещает тестовое правило | 80 |
| | `timeout_s` | таймаут одного подключения и одной внешней команды (`ufw`, `systemctl`) | 3 |
| `antivirus_test` | `eicar_timeout_s` | таймаут | 30 |
| | `poll_interval_s` | таймаут | 1 |

- **Порт** — целое число 1..65535.
- **Таймаут** (и интервал) — число (int или float, но не `true`/`false`), больше 0
  и не больше 300 секунд.
- **Имя узла** — полностью соответствует `^[A-Za-z0-9][A-Za-z0-9.-]*$`, не длиннее 253
  символов. Программа работает от root, а адрес узла M3 попадает в команду ufw, поэтому
  имя проверяется заранее и не может начинаться с «-» (не будет принято за ключ).
- **Список узлов** — непустой список имён узлов.

Каждый модуль получает свою секцию явно: `check_network.run(config["network"])`,
`check_presence.run(config["presence"], products)`,
`check_firewall.run(config["firewall_test"], products)`,
`check_antivirus.run(config["antivirus_test"])`.

Алгоритм загрузки (`common.load_config(path)`, выполняется один раз при старте `main.py`):
1. Файла нет → ошибка «Файл настроек не найден: <путь>. Установите программу:
   sudo ./install.sh».
2. Прочитать файл `load_json` (раздел 5). Ошибка → «<путь>: файл не найден или не является
   корректным JSON».
3. Взять следующий ключ из таблицы (секция, ключ, вид значения).
4. Секции или ключа нет, или значение не подходит по виду → ошибка
   «<путь>: некорректное значение <секция>.<ключ>».
5. Ключи закончились? Нет → шаг 3. Да → вернуть словарь настроек.

Неизвестные секции и ключи игнорируются: например, ключи `ping_timeout_s`, `eicar_dir`
и `control_port` из прежних версий не мешают запуску. Сообщение об ошибке одно на все
случаи, например `/etc/seccheck/config.json: некорректное значение network.tcp_port`.
`main.py` выводит его в stderr и завершается с кодом 2 без трассировки, до показа меню.

## 7. Модули проверок

### M1. Проверка подключения к интернету (`check_network.py`)

Узлы делятся на две группы, чтобы отличить полный доступ от ограниченного (белые списки
мобильных операторов, блокировки). Решение принимается по TCP-подключению: ICMP (ping)
часто режется, поэтому не используется.

Настройки: секция `network` — `ru_hosts`, `foreign_hosts`, `tcp_port`, `tcp_timeout_s`.

Алгоритм:
1. Проверить группу `ru_hosts`, затем группу `foreign_hosts` (шаги 2–3, `check_group`).
2. Для каждого узла группы по очереди: TCP-подключение к `tcp_port` с таймаутом
   `tcp_timeout_s` (`socket.create_connection`). В подробности — строка
   «<узел> TCP <порт>: да (N мс)», «…: нет» или «…: нет (ошибка DNS)»
   (`socket.gaierror`).
3. Группа доступна, если ответил хотя бы один её узел.
4. Ни одна группа не доступна → `FAIL` «нет». Если у всех узлов ошибка DNS, добавить
   в подробности «Не работает DNS: ни одно имя узла не разрешилось».
5. Доступна одна группа → `WARNING` «ограничено (доступны только российские узлы)» или
   «ограничено (доступны только зарубежные узлы)».
6. Доступны обе → `OK` «есть».

Кратких строк под итогом у M1 нет. Все итоги: `есть`, `ограничено (доступны только
российские узлы)`, `ограничено (доступны только зарубежные узлы)`, `нет`.

### M2. Наличие АВ и МЭ (`check_presence.py`)

Отвечает только на вопрос, есть ли в системе АВ и МЭ. Работают ли они, проверяют M3 и M4,
поэтому в выводе M2 нет слов про защиту, фильтрацию и работу.

В Linux нет единого реестра средств защиты (как Центр безопасности Windows), поэтому
известные продукты ищутся по файлам и службам systemd из списка `products.json`.
Продукт найден, если есть хотя бы один его файл или установлена хотя бы одна его служба.

#### Файл продуктов `products.json`

Список продуктов хранится во внешнем файле `products.json` в каталоге, где лежит `main.py`
(`os.path.dirname(os.path.realpath(__file__))`). Формат: `{"products": [ {...}, ... ]}`.

| Поле | Тип | Смысл |
|---|---|---|
| `id` | непустая строка | идентификатор (по нему M3 выбирает команды тестового правила) |
| `name` | непустая строка | название для отчёта |
| `kinds` | непустой список из `"antivirus"`, `"firewall"` | вид продукта |
| `services` | список имён служб (может быть пустым) | любая установлена → продукт найден |
| `files` | список абсолютных путей (может быть пустым) | любой существует → продукт найден |

Все поля обязательны, другие поля игнорируются. Продукты в поставке: ClamAV
(`clamav-daemon`, `/usr/sbin/clamd`), ufw (`ufw`, `/usr/sbin/ufw`), Dr.Web
(`drweb-configd`, `/opt/drweb.com/bin/drweb-ctl`, подтверждены на Ubuntu 24.04), KESL
(`kesl`, `/opt/kaspersky/kesl/bin/kesl-control`). Имена служб и пути ClamAV и KESL
на стенде не проверены: продукт может не найтись из-за неверных имён.

Файл читает программа с правами root, поэтому в формате нет полей с командами и они
не добавляются: имена служб передаются в `systemctl` только отдельным аргументом через
`run_cmd`, пути проверяются только через `os.path.exists`. Команды тестового правила МЭ
хранятся в коде (M3).

Алгоритм загрузки (`load_products(path)`, выполняется один раз при старте `main.py`):
1. Прочитать файл `load_json` (раздел 5). Ошибка → «<путь>: файл не найден или не является
   корректным JSON».
2. Корень — объект с полем `products`, значение — список. Иначе → ошибка «<путь>:
   ожидается объект {"products": [...]}».
3. Взять следующий продукт и проверить его (`check_product`): `id` и `name` — непустые
   строки; `kinds` — непустой список из `"antivirus"`, `"firewall"`; `services` — список
   имён, полностью соответствующих `^[A-Za-z0-9][A-Za-z0-9@._-]*$` (имя не может
   начинаться с «-» и не будет принято `systemctl` за ключ); `files` — список строк,
   начинающихся с «/». Не подходит → ошибка «<путь>: некорректный продукт №N».
4. Продукты закончились? Нет → шаг 3. Да → вернуть список.

`main.py` выводит сообщение в stderr и завершается с кодом 2 без трассировки: с битым
файлом программа не запускается.

#### Проверка

Состояние службы: `systemctl show -p LoadState -p ActiveState <имя>` (через `run_cmd`).
Вывод — строки «ключ=значение»: `LoadState=not-found` → служба не установлена;
`ActiveState=active` → запущена; иначе → установлена, но остановлена. Команда
не выполнилась → «состояние неизвестно» (служба не считается установленной).
`systemctl is-active` не подходит: про несуществующую и остановленную службу он одинаково
отвечает `inactive`. `# TODO(стенд)`: подтвердить формат вывода на стенде.

Настройки: секция `presence` — `cmd_timeout_s` (таймаут каждой команды `systemctl`).

Алгоритм `run(cfg, products)`:
1. Взять следующий продукт из списка `products`.
2. Проверить файлы из `files` (`os.path.exists`) и состояние служб из `services`.
   Продукт найден, если есть хотя бы один файл или установлена хотя бы одна служба.
3. Найден → добавить название в список АВ и/или МЭ по `kinds` (продукт с двумя видами
   попадает в оба). Если у продукта есть установленные службы, но ни одна не запущена, —
   после названия «(служба остановлена)». Подробности: «<название>: файл …; служба …
   запущена/остановлена».
4. Не найден → в подробности «<название>: не найден» и признаки ниже, только если
   признаки есть (служба в состоянии «неизвестно»).
5. Продукты закончились? Нет → шаг 1.
6. Итог и краткие строки «Антивирус:          <названия через запятую или «не найден»>»
   и «Межсетевой экран:   <…>»:
   - найдены и АВ, и МЭ → `OK` «найдены»;
   - найден только АВ → `WARNING` «найден только антивирус»;
   - найден только МЭ → `WARNING` «найден только межсетевой экран»;
   - ничего → `FAIL` «не найдены».

Подсказок у M2 нет.

### M3. Работоспособность МЭ (`check_firewall.py`)

Отвечает на вопрос: блокирует ли МЭ соединение, запрещённое его правилом.

Подход методички «обратиться к запрещённому ресурсу» в России ненадёжен: зарубежный ресурс
может быть заблокирован провайдером, и программа ошибочно решит, что МЭ работает. Поэтому
программа сама создаёт временное тестовое правило и подключается к одному и тому же
`IP:test_port` дважды: до правила (порт должен быть доступен) и после (соединение должно
быть заблокировано). Между подключениями меняется только наличие правила, поэтому
блокировка у провайдера на результат не влияет. От проверяющего ничего не требуется, так же
как в M4, где программа сама создаёт тестовый файл.

Правило добавляется через утилиту самого МЭ (для ufw — командой `ufw`), а не напрямую
в nft или iptables. Если МЭ выключен, его правило не применится, соединение пройдёт,
и результат честно будет `FAIL`. Правило, добавленное прямо в nft, сработало бы и при
выключенном МЭ.

Настройки: секция `firewall_test` — `host`, `test_port`, `timeout_s` (таймаут подключения
и каждой внешней команды). `run(cfg, products)` получает и список продуктов.

Алгоритм (N — `test_port`):
1. Нет прав root → `INCONCLUSIVE` «не определена — нужны права root». Подключения
   не выполняются.
2. Выбрать МЭ: перебрать продукты вида `firewall` из `products.json` по порядку и взять
   первый, который найден в системе (`check_presence.detect_product`, как в M2) и для
   которого в `TEST_RULE_COMMANDS` заданы команды тестового правила. Найденный МЭ без
   команд записать в подробности: «<Название>: способ проверки не задан».
   - Такого МЭ нет → `INCONCLUSIVE` «не определена — не найден МЭ, который программа
     умеет проверять».
3. Разрешить имя `host` в IPv4 один раз (`socket.getaddrinfo(..., AF_INET)`). Ошибка →
   `INCONCLUSIVE` «не определена — имя узла <host> не разрешается (DNS)».
4. Контрольное подключение к `IP:N` до создания правила. Не удалось → `INCONCLUSIVE`
   «не определена — тестовый порт недоступен ещё до проверки»: если порт закрыт и без
   нашего правила, вывод о работе МЭ сделать нельзя.
5. Установить обработчики SIGTERM и SIGHUP, превращающие сигнал в исключение
   (`SystemExit(128 + номер сигнала)`); Ctrl+C и так даёт `KeyboardInterrupt`. Добавить
   тестовое правило (`add_test_rule`): запрет исходящих TCP-соединений на `IP:N` с меткой
   `seccheck-test`, командой `add`; если она завершилась ошибкой `empty_error` (список
   правил пуст) — командой `add_when_empty`.
   - Команда завершилась с ошибкой → `INCONCLUSIVE` «не определена — не удалось добавить
     тестовое правило», в подробностях команда и первая строка сообщения об ошибке.
     Перейти к шагу 7.
   - МЭ ответил, что такое правило уже есть (`exists_text`) → то же `INCONCLUSIVE`,
     в подробностях «Такое правило уже есть в настройках МЭ, программа его не меняет».
     Это правило пользователя, оно не удаляется. Перейти к шагу 7.
6. Подключиться к `IP:N` ещё раз.
   - Соединение установлено → `FAIL` «запрещённое соединение не заблокировано»,
     подсказка «Проверьте, что межсетевой экран включён».
   - Не установлено → `OK` «запрещённое соединение заблокировано», в подробности — тип
     отказа (`describe_refusal`):
     - `PermissionError` (EPERM) — «соединение запрещено локальным МЭ»: ядро сразу
       возвращает EPERM, когда исходящий пакет отброшен netfilter (`# TODO(стенд)`);
     - `ConnectionRefusedError` — «соединение отклонено (правило REJECT)»;
     - `socket.timeout` — «соединение не установлено за N с (вероятно, правило DROP)»
       и пометка, что таймаут указывает на МЭ: до правила порт был доступен;
     - другая ошибка — её текст.
7. Всегда, в `finally` (при любом исходе, исключении, Ctrl+C, SIGTERM, SIGHUP): на время
   удаления игнорировать SIGINT, SIGTERM и SIGHUP (повторный Ctrl+C не должен прервать
   удаление); если правило добавлено или добавление было прервано — удалить его командой
   `delete` (`remove_test_rule`); восстановить прежние обработчики сигналов.
   - Удаление не удалось → в краткие строки «Внимание: тестовое правило не удалено,
     удалите его вручную:» и следующей строкой точная команда удаления (`sudo ufw delete
     …`). Если проверку прервали, эти строки печатаются сразу, и исключение передаётся
     дальше.
8. Вернуть итог шага 5 или 6 и предупреждения шага 7. Номер порта в итог не входит, он
   есть только в подробностях.

Подробности (только `-v`): найденные МЭ без способа проверки, проверяемый МЭ, узел и IP,
результат подключения до правила (доступен, время), добавленное правило (команда),
результат подключения после правила, тип отказа, удаление правила: выполнено / не
выполнено.

#### Команды тестового правила

Команды хранятся только в коде, в словаре `TEST_RULE_COMMANDS` в `check_firewall.py`
(ключ — `id` продукта), со списками аргументов, где `{ip}` и `{port}` заменяются адресом
и тестовым портом. В `products.json` команд нет: это файл данных, его правят вручную
(при разработке он лежит в рабочей копии пользователя), а программа работает от root. Из `products.json` берётся только `id`, по которому
выбираются заранее заданные команды. Команды заданы только для ufw; для Dr.Web и KESL
проверенного способа добавить правило из командной строки нет.

| Ключ | ufw |
|---|---|
| `add` | `ufw insert 1 deny out to {ip} port {port} proto tcp comment seccheck-test` |
| `add_when_empty` | `ufw deny out to {ip} port {port} proto tcp comment seccheck-test` |
| `empty_error` | `Invalid position` |
| `exists_text` | `Skipping` |
| `delete` | `ufw delete deny out to {ip} port {port} proto tcp comment seccheck-test` |

Почему так (проверено по исходному коду ufw 0.36.1):
- **Порядок.** Правило должно стоять раньше разрешающих правил пользователя, иначе
  разрешающее правило на тот же порт его перекроет. `ufw prepend` появился только в 0.36
  (в Astra Linux ufw 0.35). `ufw insert 1` есть в обеих версиях, но завершается ошибкой
  «Invalid position '1'», если правил IPv4 ещё нет; тогда правило добавляется обычной
  командой и всё равно оказывается первым.
- **Удаление.** ufw удаляет правило, совпадающее с описанием во всём, включая комментарий:
  удаляется только правило с меткой `seccheck-test` и тем же IP и портом. Правило
  пользователя `deny out 80/tcp` (без адреса) и такое же правило без метки не затрагиваются.
- **Правило уже есть.** Если у пользователя есть правило с тем же адресом, портом
  и направлением (даже с другим действием или комментарием), `ufw insert` ничего
  не меняет и отвечает «Skipping inserting existing rule». Программа не считает такое
  правило своим и не удаляет его.
- **Выключенный ufw.** Добавление и удаление проходят успешно («Rules updated»): правило
  сохраняется в настройках ufw, но в netfilter не попадает. После проверки оно удаляется
  и из настроек.
- Все вызовы — через `run_cmd` (таймаут, `LC_ALL=C`, `LANGUAGE=C`, без оболочки).

### M4. Работоспособность АВ (`check_antivirus.py`)

Отвечает на вопрос: реагирует ли резидентная защита (on-access) на создание тестового
файла EICAR.

Настройки: секция `antivirus_test` — `eicar_timeout_s`, `poll_interval_s`.
Константы модуля (не настройки): `FILE_NAME`, `EICAR_PARTS`.

Реакцией АВ считается только `PermissionError` (EACCES или EPERM) при записи или чтении
и исчезновение файла. Любая другая `OSError` (нет каталога, нет места на диске) — это
не реакция АВ, а `ERROR` «ошибка проверки (<что делали>: <текст ошибки>)».

Алгоритм (T — `eicar_timeout_s`, N — секунды от начала записи):
1. Собрать строку EICAR из частей, хранящихся в коде раздельно (никогда целиком).
2. Создать собственный подкаталог `tempfile.mkdtemp(prefix="seccheck_")` во временном
   каталоге системы (уникальное имя, права 700). `OSError` → `ERROR` «ошибка проверки
   (создание каталога: …)».
3. Напечатать один раз «Ожидание реакции АВ (до T с)…». Записать `eicar_test.txt`
   (`with open(...)`: файл закрывается сразу после записи, а многие АВ проверяют файл
   именно при закрытии).
4. `PermissionError` при записи или закрытии → `OK` «тестовый файл обнаружен за N с
   (запись заблокирована)». Другой `OSError` → `ERROR` «ошибка проверки (запись
   тестового файла: …)».
5. Подождать `poll_interval_s`.
6. Файл не существует → `OK` «тестовый файл обнаружен за N с (файл удалён)».
7. Попробовать прочитать файл. `PermissionError` → `OK` «тестовый файл обнаружен за N с
   (доступ к файлу заблокирован)»; файл исчез → как шаг 6; другой `OSError` → `ERROR`
   «ошибка проверки (чтение тестового файла: …)».
8. Прошло меньше T → шаг 5.
9. Иначе → `FAIL` «тестовый файл не обнаружен за T с».
10. Всегда, в `finally` (при любом исходе шагов 3–9, исключении и Ctrl+C): удалить свой
    файл и свой подкаталог (`remove_test_files`: `os.remove`, `os.rmdir`). Если удаление
    не удалось — предупреждение «Внимание: не удалось удалить <путь>: …». Если проверку
    прервали, предупреждения печатаются сразу и исключение передаётся дальше; иначе они
    добавляются в краткие строки (печатаются всегда, без `-v`: на диске остался
    тестовый файл).
11. При `FAIL` подсказка «Проверьте, что включена постоянная защита (проверка файлов при
    доступе)».

Подробности (только `-v`): путь к файлу, результат удаления файла программой; при `FAIL` —
строка «Каталог <путь> должен входить в область постоянной защиты», где путь — каталог,
в котором создан подкаталог (системный временный, обычно `/tmp`). Названия конкретных
продуктов в выводе M4 не упоминаются; настройка ClamAV для стенда описана в README.md.

### M5. Меню и отчёт (`main.py`)

Результаты хранятся в словаре `results`: идентификатор проверки → `(статус, краткие,
подробности)`.

Алгоритм работы программы:
1. `sys.dont_write_bytecode = True` до импорта модулей проекта (при запуске через `sudo`
   не создаются каталоги `__pycache__` с владельцем root). Сразу после этого: если
   кодировка `sys.stdout` или `sys.stderr` не UTF-8 (локаль C/POSIX), заменить поток на
   `io.TextIOWrapper(поток.buffer, encoding="utf-8", errors="replace",
   line_buffering=True)`; иначе первый вывод кириллицы завершится `UnicodeEncodeError`.
2. Разобрать аргументы (`--help`, `--version`, `-v`/`--verbose` — подробный вывод).
3. Загрузить настройки: `load_config` (раздел 6) из `/etc/seccheck/config.json`, затем
   список продуктов: `load_products` (раздел M2) из `products.json` рядом с `main.py`.
   Ошибка → сообщение в stderr, выход с кодом 2.
4. Напечатать заголовок: название, версия, ОС, запуск от root да/нет. Без root —
   предупреждение одной строкой: «Внимание: нет прав root. Проверка M3 не выполнится:
   для тестового правила МЭ нужны права root.».
5. Показать меню (названия пунктов 1–4 берутся из `CHECKS`), прочитать пункт.
6. 1–4 → выполнить проверку, записать в `results`, напечатать результат (раздел 4):
   итог, краткие строки, с `-v` — подробности. Исключение в модуле → `ERROR`
   «ошибка проверки (…)», программа продолжает работу.
7. 5 → выполнить M1–M4 по порядку.
8. 6 → вывести отчёт (ниже).
9. 0 или конец ввода → выход с кодом 0. Иначе → шаг 5.
10. Ctrl+C в любой момент → только перевод строки (чтобы приглашение терминала
   не склеилось с выводом) и выход с кодом 130. Перехватывается в блоке
   `if __name__ == "__main__"`. Файл EICAR и тестовое правило МЭ к этому моменту уже
   удалены (M4, шаг 10; M3, шаг 7). SIGTERM и SIGHUP во время M3 завершают программу
   с кодом 128 + номер сигнала после удаления правила.

Отчёт:
1. Заголовок: «Результаты тестирования средств защиты», название и версия, дата и время,
   имя ПК, ОС (`os_info()`), версия Python, запуск от root да/нет.
2. Для M1–M4 по порядку — результат в том же виде, что при запуске проверки: итог,
   краткие строки, с `-v` — подробности. Проверки нет в `results` → `NOT_RUN`
   «<Название>: не выполнялась».

Метки статусов: `[  OK  ]`, `[ WARN ]`, `[ FAIL ]`, `[  ??  ]` (INCONCLUSIVE),
`[ ---- ]` (NOT_RUN), `[ ERR  ]`. Ширина вывода до 100 символов: результаты пойдут
на скриншоты в записку.

Меню:

```
SecCheck 0.1 · Debian GNU/Linux 12 (bookworm) · запуск от root: да

  1  Подключение к интернету
  2  Наличие АВ и МЭ
  3  Работоспособность МЭ
  4  Работоспособность АВ
  5  Выполнить все проверки
  6  Вывести отчёт
  0  Выход

Выберите пункт: _
```

## 8. Установка (`install.sh`, `uninstall.sh`)

- Первая строка `main.py`: `#!/usr/bin/env python3` (для запуска `sudo ./main.py`).
- `install.sh` (через `sudo`): проверить root; удалить старый `/opt/seccheck`;
  скопировать `*.py`, `products.json` и образец `config.json` в `/opt/seccheck` (владелец
  root:root, каталог 755, файлы 644);
  создать `/usr/local/bin/seccheck` — sh-обёртку
  `exec /usr/bin/python3 /opt/seccheck/main.py "$@"` с правами 755. Повторный запуск —
  обновление.
- Настройки: создать `/etc/seccheck` (root, 755). Если `/etc/seccheck/config.json` нет —
  скопировать туда `config.json` проекта (root, 644). Существующий файл никогда
  не перезаписывается и не проверяется: скрипт сообщает, что файл не изменён, а об ошибках
  в нём программа скажет сама при запуске.
- `uninstall.sh`: удалить `/opt/seccheck` и `/usr/local/bin/seccheck`. `/etc/seccheck`
  не удалять, а напечатать, что настройки сохранены, и команду `sudo rm -r /etc/seccheck`.
- Почему каталог доступен на запись только root: программа работает от root, и если бы
  её код мог изменить обычный пользователь, это было бы повышением привилегий (README.md).

## 10. Проверка перед сдачей

- `vermin -q -t=3.5- --no-tips --violations .` — пустой вывод (vermin ставится только
  в среду разработки).
- `python3 -m py_compile` для каждого `.py` (проверяет только синтаксис той версии,
  которой запущен; на стенде — 3.5). При наличии Docker:
  `docker run --rm -v "$PWD":/src -w /src python:3.5 python -m py_compile *.py`.
- Строка EICAR целиком не встречается ни в одном файле проекта.
- `config.json` проходит `load_config` (и старый файл с ключами прежних версий тоже),
  `products.json` — `load_products`, в том числе
  при `LC_ALL=C LANG=C`; `LC_ALL=C LANG=C python3 main.py --help` выводит кириллицу
  без ошибок.
- Ручной запуск на стенде: все четыре проверки и отчёт (с `-v` и без), запуск без root,
  Ctrl+C во время M3 и M4; после M3 `sudo ufw status numbered` не показывает правило
  `seccheck-test`, правила пользователя на месте.

## 11. Критерии готовности

- `sudo seccheck` на стенде выполняет все проверки и выводит отчёт.
- Без root программа не падает и в отчёте объясняет, что ограничено.
- Ни одна внешняя команда не может повесить программу (таймауты везде).
- Строка EICAR целиком не встречается в исходниках; тестовый файл и тестовое правило МЭ
  удаляются даже после Ctrl+C.
- Код работает на Python 3.5.
- Код каждого модуля проверок соответствует пошаговому алгоритму из раздела 7.

## 12. Известные ограничения (для раздела «Анализ результатов»)

- Обнаружение продуктов зависит от полноты и точности `products.json`. M2 отвечает только
  на вопрос о наличии: найденный продукт может быть выключен (служба ufw в Ubuntu
  запущена и при выключенном ufw); работу МЭ и АВ проверяют M3 и M4.
- M3 проверяет, что МЭ применяет новое правило на исходящий трафик, а не всю его
  политику. Проверяется только МЭ, для которого в программе заданы команды (сейчас ufw);
  для Dr.Web и KESL M3 даёт `INCONCLUSIVE`.
- Тестовое правило запрещает соединения только на один IPv4-адрес узла и один порт.
- Если программу завершить без возможности обработки (`kill -9`, отключение питания),
  тестовое правило останется; его можно найти по метке `seccheck-test` и удалить вручную
  (README.md). SIGTERM, пришедший во время удаления правила, игнорируется.
- Поведение ufw 0.35 (Astra Linux) не проверено по исходному коду, только 0.36.1.
- M4 проверяет реакцию резидентного модуля на эталонный тестовый файл, а не способность
  обнаруживать реальные угрозы.
- Решение M1 основано на доступности выбранных узлов; на точность влияют блокировки
  и режим белых списков.
